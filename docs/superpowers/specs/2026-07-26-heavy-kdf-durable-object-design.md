# Heavy KDF Durable Object 兼容升级设计

## 目标

在保持现有 Cloudflare Workers + D1 部署模型、生产数据库、已注册账号和现有客户端兼容的前提下，将高 CPU 的服务端认证计算迁移到 Durable Object，并为后续跟随 Vaultwarden 大版本同步建立清晰的适配边界。

本阶段采用参考项目 `qaz741wsd856/warden-worker` 的 `HeavyDo` 思路，但只引入与当前仓库认证流程直接相关的能力，不进行全量业务 API 对齐，也不强制切换到 Argon2。

## 非目标

- 不迁移或重建现有 D1 数据库。
- 不删除或重命名现有用户字段，不要求用户重新注册、导入密码库或重新绑定客户端。
- 不在本阶段同步 Vaultwarden 的全部 API、通知 DO、附件系统或其他独立功能。
- 不通过降低客户端 KDF 参数来换取 CPU 使用下降。

## 现状与约束

当前服务端已经保存用户的 `kdf_type` 和 `kdf_iterations`，客户端负责生成主密码相关数据，服务端使用 Web Crypto PBKDF2-SHA256 完成二次校验。Cloudflare Worker 的普通请求 CPU 预算有限，因此登录、注册和需要主密码校验的账户操作可能与普通 API 请求争用执行资源。

兼容性是硬约束：已有用户必须继续使用其现有 KDF 参数和数据库记录；新逻辑出现错误时，不能让存量账号失去登录能力。所有数据结构变更必须是新增式、可回滚式的迁移。

## 架构

新增 `HeavyDo` Durable Object，绑定名为 `HEAVY_DO`。主 Worker 保留现有 API 路由和 D1 绑定，并将高 CPU 的认证请求转发给 DO。DO 将 `worker::Request` 转换为 HTTP 请求，复用现有 Axum router 和业务处理器，避免维护两套认证实现。

### 主 Worker

- 继续处理普通 API、同步、密码项、文件、发送项、设备和管理请求。
- 识别需要高 CPU 认证计算的入口，并将原始请求转发到 `HeavyDo`。
- 保留现有响应状态码、JSON 字段、Cookie 和 Authorization 行为。
- 为 DO 转发请求增加仅内部使用的标记；DO 看到该标记后直接执行，防止主 Worker 与 DO 循环转发。
- DO 不可用或转发失败时，按明确的兼容策略执行现有路径；不得重复提交有副作用的注册、改密请求。

### HeavyDo

- 暴露与主 Worker 相同的 Axum API 入口。
- 复用现有数据库访问、模型、错误和 JWT 生成逻辑。
- 只承载高 CPU 请求，不把同步等大响应普通接口迁移到 DO。
- 使用与主 Worker 相同的环境变量和 D1 绑定。
- 不在 DO 状态中保存密码、JWT 或用户密钥；DO 状态仅作为运行时承载，不作为业务数据存储。

## 高 CPU 请求范围

首批迁移范围如下：

- `POST /identity/accounts/prelogin`
- `POST /identity/connect/token`
- 注册相关账户接口
- 修改密码
- 修改邮箱等需要校验主密码的账户接口

具体路径以当前 router 和客户端实际调用为准；若某个入口包含不可安全重试的写操作，必须先完成幂等性检查，再允许 DO 失败回退。

## KDF 与渐进升级

### 兼容校验

- 读取用户记录中的现有 `kdf_type` 和 `kdf_iterations`。
- 对已有用户严格使用记录中的参数进行校验，不使用新的全局默认值覆盖旧配置。
- 认证失败继续返回现有通用错误，不泄露邮箱是否存在或 KDF 细节。
- 二次 KDF 的输入、输出编码和比较方式保持现有格式，确保旧数据无需转换。

### 渐进升级

本阶段为服务端二次 KDF 预留升级接口，但不强制迁移：

- 认证成功后，比较用户当前参数与服务端目标参数。
- 只有在目标参数明确启用、计算成功且写回不会影响登录结果时，才更新对应的服务端字段。
- 写回失败不使本次登录失败，并记录不包含敏感数据的诊断信息。
- 不改变客户端声明的 KDF 配置，不修改用户密码库加密密钥。
- 未来切换更高成本算法时，通过版本化字段/标记区分新旧格式，并保留旧格式验证窗口。

## CPU 与安全控制

- 对登录等敏感入口增加 Cloudflare Rate Limiting，优先按邮箱和来源地址组合限制。
- 避免在一次请求中重复读取用户记录、解析 KDF 配置或初始化不变的认证数据。
- 主 Worker 只做轻量路由判断，重计算集中在 DO。
- 限制 DO 请求体大小，避免把大请求误送入重计算通道。
- 内部转发标记不能由外部客户端伪造为可信来源；应采用不可冲突的内部 header/上下文策略，并在边界处清理。
- 不记录密码、主密码哈希、JWT、Cookie、TOTP 或 D1 密钥。

## 数据库与部署迁移

### 数据库

- 优先复用现有 `users` 字段，不新增破坏性变更。
- 如渐进升级确实需要独立版本/状态字段，只新增可空字段并提供默认行为。
- 所有迁移脚本同时更新 `sql/schema.sql`、`sql/schema_full.sql` 和对应 `migrations`/`sql/migrations` 文件（以仓库现有约定为准）。
- 不删除旧字段、不重建用户表、不覆盖现有 D1 binding。

### Wrangler

增加 `HEAVY_DO` Durable Object binding 和一次性 migration，例如：

- `new_sqlite_classes = ["HeavyDo"]`
- 保留现有 Worker 名称、D1 数据库名称和 database ID。
- 增加可选的服务端 KDF 目标参数配置，默认关闭渐进升级，避免部署后行为突变。
- 增加登录限流配置，并确保测试/生产配置分别可控。

## 测试与验收

### 单元/静态检查

- `cargo fmt --check`
- `cargo check`
- Worker release build/check
- 路由转发不会触发循环调用
- KDF 旧格式、新格式和错误参数覆盖测试

### 接口回归

- 旧账号可登录、刷新/记住设备、同步、修改密码和修改邮箱。
- 新注册账号可完成登录和同步。
- Web、Android 及已有移动端请求格式保持兼容。
- DO 成功、DO 暂时失败和兼容回退路径的状态码/响应 JSON 一致。
- 登录限流只限制敏感入口，不影响普通同步和密码库读取。

### 数据安全

- 迁移前后 D1 用户记录可直接读取。
- 认证日志不包含敏感字段。
- 渐进升级写回失败不会导致登录失败。
- 不重复执行不可安全重试的账户写操作。

## 后续 Vaultwarden 同步边界

将认证/KDF 逻辑、DO 适配、响应模型和数据库兼容层保持为相对独立的模块。后续跟随 Vaultwarden 大版本时，优先同步协议字段、KDF 参数和认证行为；普通业务 API 与 Cloudflare 专属运行时适配分开评估，避免把上游升级直接等同于数据库重建或全量重写。

## 实施顺序

1. 抽取可复用的认证/KDF服务函数和兼容错误处理。
2. 增加 `HeavyDo`、内部转发和防循环机制。
3. 迁移只读/可安全重试的认证入口，再迁移账户写入口。
4. 增加渐进 KDF 升级开关、限流和敏感日志审计。
5. 更新 Wrangler migration、部署文档和冒烟测试。
6. 在测试 D1 上完成旧账号、新账号、DO失败和回退路径验证，再发布生产。
